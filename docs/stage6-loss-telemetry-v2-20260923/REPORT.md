## Instrumentation

1. Sampling: independent sampler thread, nominal 100 ms wait after each query (at most approximately 10 queries/s plus initial query). No catch-up burst. Actual query begin/end QPC retained. Delayed queries reduce rate and remain visible; sub-100ms transients can still escape observation.
2. Session counters: ControlTrace QUERY EventsLost, RealTimeBuffersLost, LogBuffersLost, NumberOfBuffers, FreeBuffers, BuffersWritten, status. Failed queries have null EventsLost; zero must not be inferred. The original session properties buffer/counters and exit decision remain unchanged.
3. Session binding: distinct run-directory name, exact session string, authority/detail channel, QPC frequency and origin. Requested 64 KiB / 4 / 64 / 1s parameters and actual StartTrace-returned configuration are recorded. Real-time/system flags, per-processor buffering, QPC clock, process/file/registry keywords and absence of explicit stackwalk/rundown are described. Provider calls themselves remain byte-identical.
4. Progress: received and completed callback counters remain distinct; selected counts, receipt/completion QPCs, active-callback start, interval deltas, callback duration sum/max and histograms. CPU time and live/signaled state come from a duplicated consumer THREAD handle. No PID lookup substitutes for it.
5. Histograms: fixed 64-bin power-of-two tick ranges. Offline p50/p95/p99 are lower/upper bounds, not exact quantiles. Selected-event timestamp-to-callback lag is separate from execution duration. No producer event count is inferred from selected records or callbacks.
6. Slow spans: >=5 ms diagnostic threshold only. Metadata, process/image metadata, guard wait/hold, serialization, queue admission, segment rotation, write, flush, close and named other spans. Begin/end QPC, thread ID, start/end queue items/bytes/pending count, previous/latest loss-sample references. Nearest succeeding sample can be joined offline; no ControlTrace or disk call is added to the hot callback for a slow span. Span buffer contention/overflow is explicit diagnostic failure.
7. Writer telemetry: atomically published queue state, admitted counts, records/bytes completing durable flush, completed finalizations. DurableSink queue items include in-flight writer work; TraceSink queue items exclude its active segment. Pending refers to the separate durable finalizer backlog; TraceSink has no such queue. Atomically read fields are individually observed, not a transactionally coherent queue snapshot. Final queue/counter state is also serialized after writer completion. Flush counts are diagnostic and do not imply successful hash verification or acceptance.
8. Clock alignment: common QPC domain, session start and readiness QPC. Cleanup entry/deadline remains in the existing `cleanup-origin-v3.json` and Phase A. The offline binder reopens, hashes and checks these artifacts and exact run/session/frequency equality. The tracer sidecar explicitly has null cleanupEntryQpc until this external binding; it does not invent a clock or add callback-path file reads.
9. Bounds: 16,384 samples; 4,096 slow spans; 21,200,896 bytes of reserved record storage per tracer, plus fixed counters/histograms and bounded final serialization. No diagnostic queue of arbitrary ETW payloads. Overflow/query/CPU/clock errors are explicit. No callback file write or durable flush. Sidecar serialization/write occurs after consumer/sampler closure and writer finalization; it consumes existing lifecycle time, never a new deadline.
10. Failure behavior: sidecars cannot issue an acceptance seal. Missing/failed sidecar, errors, overflow, bad run/session/frequency, stale binding or counter regression rejects diagnostic qualification. Any observed ETW/buffer loss remains ineligible. The unchanged checker and original lifecycle evidence are still mandatory; valid telemetry is never a substitute. Existing fail-closed loss decisions, provider settings, queue limits and observer shutdown order are unchanged.
